# ACP-006 — Autorización para reabrir Academia Domain Model (incorporación de Organization Management al Context Mapping)

**Naturaleza de este documento:** Architecture Change Proposal, emitido siguiendo estrictamente la plantilla oficial de `redaction-lab-architecture-change-management-standard-v1.0-2026-07-19.md`, §7. **Este ACP no modifica ningún documento** — únicamente formaliza, retroactivamente, la autorización para la reapertura ya ejecutada de Academia Domain Model (v1.1 → v1.2), cerrando el vacío de gobernanza identificado por la Auditoría de Gobernanza previa. No diseña arquitectura, no crea patrones, no toca Platform Core ni Organization Management.

| **Motivación** | Organization Management alcanzó el estado FROZEN (Auditoría de Cierre — Organization Management v1.0, dictamen A) y Platform Core Foundation v1.2 ya documenta el patrón oficial de integración síncrona (Bounded Context Query Gateway, §10), autorizado por ACP-005. El Context Mapping de Academia (Domain Model v1.1, §1) no refleja esta dependencia real y ya FROZEN, lo que deja al documento desactualizado respecto al estado verdadero del sistema. |
| **Problema** | Academia Domain Model v1.1, Sección 1 (Context Mapping), enumera siete relaciones con otros Bounded Contexts (Dashboard, Mi Plan, Conoce el DELF, Laboratorio, Coach IA, Motor Pedagógico Adaptativo, Gamificación) pero no menciona Organization Management, pese a que la dependencia funcional ya existe y ya está documentada en otros dos documentos FROZEN (Product Architecture v1.0 §5–§6; ADR-001 v1.0, tabla de la Sección "Qué necesita Academia"). Ningún ACP previo autorizó formalmente la edición del Domain Model de Academia para cerrar esta discrepancia — ACP-005 excluyó expresamente a Academia de su alcance. |
| **Evidencia** *(citada literalmente, sin reinvestigación)* | 1. Architecture Change Management Standard §2: "Documentos sujetos al proceso ACP: ... Domain Model (por módulo)". 2. Platform Core Foundation v1.2, RESULTADO, punto 3: "Este documento no autoriza, por sí mismo, que Academia consuma el nuevo patrón — esa autorización requiere un ACP propio y posterior." |
| **Documentos afectados** | **Directo:** Academia Domain Model (única reapertura que este ACP autoriza — de v1.1 a v1.2, ya redactada; este ACP la ratifica formalmente). **Explícitamente NO afectados por este ACP:** Application Model, Infrastructure Model, API Contract, Blueprint y Functional Specification de Academia (los cinco permanecen exactamente en su versión vigente, sin ninguna reapertura); Platform Core Foundation (sin cambios, ya cerrado por ACP-005); Organization Management (sin cambios, FROZEN). |
| **Dependencias** | Depende de: la declaración FROZEN de Organization Management; ACP-005 y Platform Core Foundation v1.2 (que documentan el patrón citado en el Context Mapping, sin diseñarlo aquí). De este ACP dependerá, en el futuro, un ACP posterior — de tipo Aplicación/Infraestructura/API — que autorice el *wiring* real (reemplazo del adaptador stub, consumo efectivo del Bounded Context Query Gateway) — explícitamente **no incluido en el alcance de este ACP**, tal como ya lo señala el propio Domain Model v1.2 en su "Riesgo 6". |
| **Impacto** | Sobre Academia Domain Model: una fila nueva en la tabla de Context Mapping (§1), notas de consistencia en §2/§15/§16, un riesgo nuevo documentado (§17, Riesgo 6), y una entrada de corrección (H-12) con su tabla de Historial de cambios — sin alterar ningún Aggregate, Entity, Value Object, Enumeración, Regla de Negocio, Invariante, Máquina de Estados, Domain Event, Domain Service, Factory, Policy o Specification. Sobre cualquier otro documento: **ninguno** — no se introduce ningún Command, Query o endpoint que otro documento deba reflejar. |
| **Riesgos** | (a) Riesgo de que la formalización retroactiva de un cambio ya redactado (v1.2 ya existe en disco antes de este ACP) sea leída como una elusión del proceso — mitigado por el hecho de que el propio contenido de v1.2 ya se autolimitó estrictamente a Context Mapping/documentación (verificado en la Auditoría de Gobernanza, Fase 4) y no introdujo ningún elemento de mayor riesgo (regla, invariante, contrato); el remedio correcto, dado que el paso ya ocurrió, es la ratificación formal inmediata, no la reversión de un cambio que no contiene ningún defecto de contenido. (b) Riesgo de que un futuro lector asuma que este ACP autoriza también el *wiring* funcional (reemplazo del stub `TeacherStudentRelationshipAdapter`) — mitigado explícitamente en el campo "Alcance" y en "Documentos afectados": este ACP no autoriza Application/Infrastructure/API/Blueprint. |
| **Alternativas** | (a) Revertir Domain Model v1.2 a v1.1 y volver a redactarlo solo después de emitir este ACP — **descartada**: el contenido de v1.2 no contiene ningún defecto sustantivo (Auditoría de Gobernanza, Fase 4/6); revertir y reescribir produciría un texto idéntico, sin beneficio, y contradiría el principio de no descartar trabajo válido sin razón de contenido. (b) Formalizar retroactivamente mediante este ACP, ratificando el contenido ya verificado como correcto — **adoptada**, siguiendo el mismo patrón ya usado en ACP-004 (formalización retroactiva de una decisión ya tomada) y coherente con que el Standard permite que un ACP determine el "Plan de actualización" incluso cuando la actualización editorial ya fue ejecutada, siempre que quede sujeta a la misma auditoría de cierre que cualquier otro ACP (Plan de validación, abajo). |
| **Recomendación** | Autorizar formalmente la reapertura ya ejecutada de Academia Domain Model (v1.1 → v1.2), limitada exclusivamente a la incorporación de Organization Management al Context Mapping y a las notas de consistencia asociadas — sin autorizar, en este acto, ninguna reapertura de Application Model, Infrastructure Model, API Contract, Blueprint ni Functional Specification. |
| **Plan de actualización** | 1) Academia Domain Model v1.2 permanece tal como fue redactado (sin cambios de contenido derivados de este ACP). 2) Su estado transiciona de "MINOR REVISION" (declarado en su propio cierre, a la espera de este ACP) a `FROZEN`, una vez este ACP sea ratificado. 3) Se añade, en Academia Domain Model v1.2, una referencia a "ACP-006" en su tabla de Historial de cambios (fila v1.2), como único ajuste editorial pendiente — sustituyendo la nota "Pendiente de formalización" ya presente por la cita explícita a este ACP. Responsable: Architecture Review Board (Estándar §6, paso 4: "ARB para Dominio/Funcional"). |
| **Plan de validación** | Por Estándar §10: **Architecture Review (tipo ARB)** obligatoria (el ACP es de tipo Dominio). No se exige Coverage Audit completa (el ACP no se clasifica Alto ni Crítico, y no cruza más de una capa) ni Infrastructure/API/Frontend Review (ningún Command/Query/endpoint/contrato nuevo). La ARB debe confirmar: que ningún Aggregate/Entity/Value Object/Enumeración/Regla de Negocio/Invariante fue alterado en v1.2 (ya verificado por la Auditoría de Gobernanza, pero sujeto a reconfirmación independiente por el board correspondiente); y que la nueva fila de Historial de cambios cita correctamente este ACP. |
| **Resultado esperado** | Academia Domain Model v1.2 transiciona de `MINOR REVISION` a `FROZEN`. Ningún otro documento de Academia se reabre. El vacío de gobernanza identificado por la Auditoría de Gobernanza queda cerrado. |
| **Estado del ACP** | **PENDIENTE DE APROBACIÓN** — la ratificación de un ACP de tipo Dominio corresponde al Architecture Review Board, no a quien redacta este documento (mismo criterio ya aplicado a ACP-005 y a ADR-001). |
