# ACP-007 v1.1 — Apertura formal para modificar el Architecture Change Management Standard v1.0 (vacío normativo: regularización retroactiva)

**Naturaleza de este documento:** Architecture Change Proposal, emitido siguiendo estrictamente la plantilla oficial del propio Standard, §7. **Este ACP no modifica ningún documento** — únicamente solicita y, de aprobarse, autoriza el estudio de cómo cerrar el vacío normativo ya identificado en el propio Architecture Change Management Standard v1.0. No se diseña aquí ningún texto de reemplazo, ningún estado nuevo, ninguna rama de flujo ni ningún campo de plantilla.

## Plantilla oficial (Sección 7 del Standard)

| Campo | Contenido |
|---|---|
| **ID** | ACP-007 |
| **Título** | Apertura formal para modificar el Architecture Change Management Standard v1.0, con el fin de resolver el vacío normativo de regularización retroactiva de modificaciones ya ejecutadas sobre documentos Frozen |
| **Fecha** | 2026-08-02 |
| **Autor** | Architecture Review Board (origen: rechazo formal de ACP-006 v1.1, fundamentado exclusivamente en el §11 del propio Standard, sin objeción al contenido técnico del cambio subyacente) |
| **Tipo** *(corregido — C-03)* | **Documentación.** El Standard §4 define este tipo como: *"Agregar trazabilidad, notas aclaratorias o ejemplos faltantes, sin alterar comportamiento."* Se reconoce, en esta misma justificación, que el Standard no define una categoría de encaje perfecto para un cambio sobre sí mismo — de los diez tipos enumerados en §4, ninguno nombra explícitamente "cambios al propio Standard." "Documentación" se selecciona por ser la categoría existente más próxima a la naturaleza del cambio (cerrar una ausencia de mecanismo mediante su documentación formal), tal como exige la corrección C-03: el campo contiene una categoría válida de §4, y la limitación se explica aquí, no en el campo. |
| **Clasificación de impacto** *(corregido — C-02)* | **Bajo.** Standard §5, cita literal: *"Bajo \| 1 documento afectado. \| Ningún consumidor externo al documento se ve afectado; sin cambio de comportamiento observable."* Este ACP afecta directamente un único documento (el propio Standard); no introduce todavía ningún comportamiento nuevo (el mecanismo se difiere al ciclo de Actualización); ningún documento consumidor del Standard se ve afectado por este acto. No se aplica ninguna analogía con la clasificación que ACP-005 usó para sí mismo — esa comparación fue retirada por no estar respaldada en el texto literal del §5, cuyos ejemplos de "elemento nuevo de primera clase" (Command, Query, endpoint, Aggregate) son construcciones técnicas de un Bounded Context, no de un documento de gobernanza. |
| **Motivación** | Cerrar el vacío normativo que produjo el rechazo automático de ACP-006 v1.1 por parte del Architecture Review Board, sin que dicho rechazo haya cuestionado el contenido técnico del cambio subyacente. |
| **Problema** *(ajustado — C-01, cambio mínimo necesario)* | El Standard no contempla, en §3, §6, §7, §9, §11 ni §12, ningún mecanismo para regularizar una modificación de un documento Frozen ya ejecutada antes de la existencia de un ACP aprobado — dejando a Academia Domain Model v1.2 sin ruta documentada hacia ninguno de los seis estados oficiales. (El §1 del Standard describe el propósito general del proceso ACP —incluida la prevención de "congelación prematura de documentos con vacíos conocidos, sin un mecanismo formal para cerrarlos después"— como contexto de por qué este vacío es relevante para el proyecto; no se usa como prueba de que el vacío específico exista, lo cual se demuestra exclusivamente con §3, §6, §7, §9, §11 y §12.) |
| **Evidencia** *(corregido — C-01, I-01)* | La demostración del vacío descansa exclusivamente sobre: 1) Standard §3 — cita literal de `MINOR REVISION`: *"Estado transitorio de un documento ya `FROZEN` que tiene una o más decisiones **ya aprobadas (vía ACP)** pendientes de integrarse mecánicamente en su texto."* Ningún estado cubre el orden inverso. 2) Standard §6 — cita literal: *"Ningún paso puede omitirse. Un ACP que pretenda saltar directamente de 'Solicitud' a 'Actualización' se rechaza automáticamente (Sección 11)."* No se describe el caso en que "Actualización" ocurre sin que exista ninguna "Solicitud" previa. 3) Standard §7 — los 19 campos de la plantilla no incluyen ninguno para declarar una modificación ya ejecutada antes del ACP. 4) Standard §9 — cita literal de la cadena de trazabilidad: *"Documento original (FROZEN) → ACP → Documento actualizado (MINOR REVISION) → Nueva versión (FROZEN)"* y *"ninguna versión nueva sin su ACP citado."* 5) Standard §11 — cita literal: *"Un ACP debe rechazarse automáticamente, sin pasar a Revisión, si... propone o asume que un documento Frozen ya fue modificado directamente, sin pasar por este proceso"* — corroborado por el rechazo real ya ejecutado de ACP-006 v1.1 exclusivamente por esta cláusula. 6) Standard §12 — el formato oficial de Historial de cambios no contempla una fila para esta secuencia invertida. **Nota sobre fuente secundaria (I-01):** la "Nota de gobernanza" de Academia Domain Model v1.2 menciona "ACP-004" como precedente de formalización retroactiva ya practicado en el proyecto. Esta referencia se mantiene únicamente como **fuente secundaria declarada explícitamente** — ACP-004 en sí mismo nunca fue leído ni verificado en ninguna etapa de esta investigación, por lo que **no se utiliza como evidencia principal** del vacío normativo, que se sostiene íntegramente en los seis puntos anteriores. |
| **Documentos afectados** | **Directo:** Architecture Change Management Standard v1.0. **No modificados:** Platform Core Foundation, Academia (todos sus documentos), Organization Management, Product Architecture, ADR-001. |
| **Dependencias** | Depende del rechazo formal de ACP-006 v1.1 por el Architecture Review Board. De este ACP dependerá, en el futuro, un ACP posterior que aplique el mecanismo ya estudiado y documentado a la disposición final de Academia Domain Model v1.2 — explícitamente no incluido en el alcance de este ACP. |
| **Impacto** | Sobre el Standard: adición de, como mínimo, un mecanismo nuevo (alcance exacto a determinar en el ciclo de Actualización, no aquí). Sobre cualquier otro documento: ninguno todavía. |
| **Riesgos** *(ampliado — M-01)* | Los ya identificados: Academia Domain Model v1.2 sin ruta documentada mientras este ACP no se resuelva; ausencia de autoridad superior al Architecture Change Control Board dentro del proyecto para resolver ambigüedades del documento de mayor jerarquía normativa; continuidad de la práctica no codificada de formalización retroactiva. **Riesgo añadido (M-01):** *"La referencia a ACP-004 constituye evidencia secundaria no verificada."* |
| **Alternativas** | (a) No modificar el Standard y tratar cada futuro caso de modificación ya ejecutada como un rechazo automático definitivo, sin ruta de regularización — descartada por evidencia documental (§3/§6/§7/§9/§11/§12, ver "Evidencia"). (b) Modificar el Standard para incorporar un mecanismo de regularización retroactiva — adoptada como objeto de estudio de este ACP, sin diseñar aquí su contenido concreto. |
| **Recomendación** | Autorizar la reapertura del Architecture Change Management Standard v1.0 exclusivamente para estudiar y documentar un mecanismo de regularización retroactiva — sin prescribir aquí su diseño concreto, siguiendo el mismo patrón de alcance (no de clasificación) ya empleado por ACP-005 para Platform Core Foundation. |
| **Plan de actualización** *(ajustado — C-04, cambio mínimo necesario para coherencia con el Plan de validación)* | 1) El Standard pasa a `MINOR REVISION` (§3). 2) Se estudia el mecanismo necesario contra las seis secciones identificadas (§3, §6, §7, §9, §11, §12). 3) Si se aprueba, se documenta e incorpora al texto del Standard. 4) El Standard pasa a una nueva versión FROZEN. **Responsable: Architecture Change Control Board (ACCB)** — corregido de la versión anterior, que asignaba responsabilidad conjunta al Architecture Review Board; ver justificación en "Plan de validación". |
| **Plan de validación** *(corregido — C-04)* | Revisión por el **Architecture Change Control Board (ACCB)**, no por el Architecture Review Board. Justificación literal: Standard §6 asigna board de Revisión por tipo — *"ARB para Dominio/Funcional, IRB para Infraestructura, un board equivalente para API/Frontend cuando se constituya, el propio ACCB para Platform Core y para cualquier cambio que cruce más de un tipo"* — ninguna de estas asignaciones nombra el tipo "Documentación." Ante esa ausencia de asignación explícita, se recurre al propio encabezado del Standard, que declara: *"Emisor: Architecture Change Control Board (ACCB), Rédaction Lab"* — el ACCB es, por designación literal del propio documento, el cuerpo emisor y con autoridad sobre el Standard mismo. La revisión debe confirmar que el mecanismo resultante: (a) cierra el vacío evidenciado en las seis secciones citadas; (b) no reabre ninguna resolución arquitectónica ya aprobada (A-01–A-10); (c) no debilita el criterio de rechazo automático del §11 para los casos que sí busca prevenir (modificaciones no divulgadas o de mala fe). |
| **Resultado esperado** | Architecture Change Management Standard v1.x (FROZEN), con un mecanismo formal de regularización retroactiva ya definido, permitiendo que un ACP posterior resuelva la disposición final de Academia Domain Model v1.2 sin activar automáticamente el §11. |
| **Estado del ACP** | **PENDIENTE DE APROBACIÓN** |
